# 캐릭터·상태 효과·보스·벽·10층 확장 검토 (2026-09-29)

이번 요청은 검토 우선이다. 게임 코드와 운영 릴리스는 변경하지 않았다. 금발 캐릭터의 “예시” 이미지는 이번 요청에 첨부되지 않아 구체적인 머리 모양·의상은 아직 대조하지 못했다. 현재 코드는 Canvas 도형 기반이다.

## 1. 금발의 미형 주인공
- 현재 src/rendering/hero.js는 짧은 짙은 머리, 진한 윤곽, 좁은 눈, 강철 갑옷의 측면 궁수다. src/rendering/pixel-world.js가 좌우 반전하여 그린다. 움직임과 활 공격은 그대로 재사용 가능하다.
- 권장: 얼굴과 머리를 집중 수정. 이마 위 밝은 금발 앞머리·머리 뒤쪽 작은 가닥, 선명한 눈썹/눈, 밝은 피부 명암, 정돈된 얼굴선을 1~3px 픽셀로 표현한다. 갑옷은 은회색·짙은 청색을 유지하고 금 장식은 최소로 둬 머리/얼굴이 주인공의 핵심 식별점이 되게 한다. 화면의 약 30px 인게임 크기에서 읽히도록 먼저 실루엣 검증.
- 8방향이라는 기존 QA는 이동 입력의 8방향이다. 현재 스프라이트는 실제로 좌우 반전된 측면 2방향으로 그려진다. 이 요청만으로 8방향 새 스프라이트를 만들지 않는 편이 범위를 제어하기 쉽다. 예시가 확인되면 앞머리 길이·머리 묶음·눈매·의상 비율을 최종 결정.

## 2. 몬스터 둘레의 사각·원형 효과
- 둥근 정예 효과 일부는 이미 그라데이션이지만 선명한 테두리는 별도로 남아 있다: src/combat/elites.js의 보호받는 적 파란 사각형, src/combat/elements.js의 빙결 파란 사각형과 시련 용사 보라 원, src/rendering/atmosphere.js의 7층 문지기 격노 원. 프리즘 보호막·링 탄막의 안전 틈·왕의 심판 범위는 전투 정보이므로 별도 분류.
- 권장: 보호는 몸 주변 저채도 청색 발광+작은 방패 픽셀, 빙결은 반투명 얼음 결/서리 입자, 시련은 은은한 보라 광채+명칭, 격노는 약한 붉은 열기와 눈·무기 색으로 구분한다. 선명한 외곽선을 없애더라도 무슨 상태인지 알 수 있게 각각 다른 모티브와 문구를 유지한다.
- 위험 범위·안전 틈은 완전 삭제하면 회피 정보가 사라질 수 있다. 해당 표시의 선 두께/불투명도만 줄이거나 안쪽 색 면으로 바꾸고 실제 판정 반경과 위치를 검증한다. 먼저 각 효과가 보이는 화면 캡처로 사용자가 지목한 테두리를 매칭한다.

## 3. 보스 외형
- 2층 녹슨 파수꾼(src/rendering/pixel-world.js), 4층 프리즘(src/rendering/pixel-world.js), 6층 독성 슬라임(src/rendering/pixel-world.js), 8층 왕(src/rendering/upper-visuals.js)이 별도 코드 그림이다. 자세/페이즈는 src/rendering/boss-poses.js와 현재 전투 상태를 사용한다.
- 권장: 파수꾼은 비대칭 녹슨 갑주·큰 망치·투구 균열, 프리즘은 중심 코어와 층이 다른 파편·굴절광, 슬라임은 내부 핵/기포·분열 단계별 눈/왕관 변화, 왕은 왕관·망토·검의 실루엣과 65%/30% 페이즈 차이를 강화한다. 단순 색 변경보다 실루엣 차이를 우선한다.
- 우선 4보스 정지/공격 준비/공격/회복을 한 장의 시트로 비교. 적 체력·판정·공격 타이밍은 그대로 두고 도형/색/애니메이션만 수정. 가시성 테스트는 PC와 모바일 화면 모두 필요.

## 4. 벽체 질감
- src/rendering/stone-walls.js는 외곽/내부를 동일한 48×40 월드 격자, 면색 #3c4742, 줄눈 #11191b로 그린다. 960×540 방 이미지를 최대 4장 캐시한다. 예전의 큰 벽 렌더링 버벅임을 줄인 구조다.
- 권장: 블록마다 낮은 대비의 윗면/아랫면 명암, 드문 금·균열·마모 픽셀을 결정적 좌표 해시로 추가. 외곽과 내부는 같은 함수/팔레트를 사용하고, 한 블록에 장식 1~3개 이내. 이끼는 일부 블록에만 두어 번쩍이는 격자 인상을 피한다. 벽 경계 밖으로 장식이 새지 않도록 기존 clip을 유지한다.
- 캐시 생성 시만 추가 그림을 실행하게 하고 정적 이미지 1회 복사 구조를 보존. 7방 형태·PC/모바일 화면·외곽 연결·대형 벽 캐시 비용을 함께 검사. 충돌/길찾기/저장은 변경할 필요가 없다.

## 5. 10층 확장
- 새 도전은 src/game/engine.js에서 8층 생성. 7층 문지기/8층 왕좌 이벤트가 고정되고 왕 처치 시 열쇠·귀환 시작. 층명·색·방 장식도 8개이며 저장 검증은 층 수 [2,4,6,8]만 허용한다. src/game/game.js에는 8층 왕 유물함과 계단/스토리 문구의 고정 참조가 있다.
- 서버 랭킹도 8층 전용: api/ranking_api.py가 방 배열 길이8과 마지막 층 방 수8, 방문 층 집합 0~7을 요구한다. 현재 규칙 ranking-v1/시즌 BETA-1의 점수·시간 비교에 10층 기록을 섞으면 공정하지 않다.
- 권장 구조: 현재 8층 왕 전투를 중간 정점으로 살리고, 9층 새 지역과 10층 새 최종 보스를 추가한다. 왕의 열쇠 지급은 10층 결말로 옮기고 8층 왕 뒤의 계단/서사를 설계한다. 왕이 최종 보스여야 한다면 8층 왕좌를 10층으로 옮기는 대안도 가능하며 이 선택에 따라 이야기와 콘텐츠 범위가 달라진다.
- 구현 순서: (1) 9/10층의 지형·적/보스·보상·스토리 및 플레이 시간 목표 합의, (2) 층 수/왕 이벤트의 고정값을 공통 진행 설정으로 정리, 기존 8층 저장의 완주 규칙 보존, (3) 저장/지도 생성/계단 왕복/하강/랭킹 서버 검증을 8층·10층 모두 검사, (4) 새 시즌·규칙으로 10층 랭킹을 분리하고 기존 BETA-1 기록/조회 보존, (5) 난이도·시간/점수 분포 플레이테스트.
- 단순히 Array.from 길이만 10으로 바꾸면 새 층은 상층 적을 재사용하고 8층 왕이 최종 보스가 아니게 되며, 저장/서버 순위가 막힌다. 10층은 별도 기획·구현 단위로 진행하는 것이 적절하다.
