# Spirebound 출시 품질 로드맵 검토 (2026-09-30)

이 문서는 **웹 게임 공개 출시**를 가정한 권장 순서다. 스토어 앱 출시를 목표로 한다면 패키징·심사·기기 정책 단계를 별도로 설계해야 한다. 아래는 제안이며 범위/완료 판정은 사용자 결정 후 TODO로 확정한다.

## 현재 근거와 빈틈
- 이미 확보: 8층/10층 캠페인과 분리된 서버 랭킹, HTTPS/운영 백업·점검, 전체 자동 테스트 382개, Edge PC·모바일 화면 에뮬레이션의 주요 기능 QA. 최신 세부 결과는 WORK_STATUS.md.
- 확인하지 못함: 사람이 조작한 8층/10층 완주 경험, 실제 iPhone/Android 기기의 조작·프레임/발열, 브라우저별 장시간 안정성, 사용자 기기의 벽체 버벅임 해소 여부. 자동 시뮬레이션과 에뮬레이션은 이를 대체하지 않는다.
- 제품 표현의 빈틈: `index.html` 머리글은 아직 “EIGHT FLOORS”와 “베타 준비 0.31”을 표시한다. 자산은 타이틀 이미지·폰트가 중심이고 `warning-audio.js`의 위험 경고음 외에 지속적인 음악/전투 피드백 사운드가 없다. 브라우저 저장은 기기 간 동기화되지 않으며 백업은 같은 서버 디스크에 있다.

## 권장 단계와 통과 기준

1. **실제 플레이 기준선과 문제 목록.** 두 캠페인을 처음 보는 플레이어에게 설명 없이 시켜 보고, 첫 기술 선택·첫 사망·각 보스·귀환·랭킹 등록까지 걸린 시간과 막힌 지점, 피격 원인·실패 후 재도전 의사를 기록한다. 사용자 본인과 소수 외부 테스터의 PC/실제 모바일 플레이를 구분해 모은다. 통과: 반복되는 혼란·불공정 사망·진행 막힘을 우선순위별로 재현 가능한 문제로 정리하고 출시 대상 캠페인(8층/10층)을 확정한다.
2. **핵심 전투 감각과 콘텐츠 다듬기.** 1단계에서 드러난 난이도와 정보 전달 문제부터 고친다. 9·10층 보스 예고/피격/전환 가독성, 화살·피격·보상·보스의 소리, 일관된 캐릭터/배경/효과, 첫 회차 안내와 죽음 후 다음 행동을 한 묶음으로 다룬다. 설정에 음악/효과음 볼륨·음소거와 강한 화면 효과 완화 선택을 둔다. 통과: 각 공격을 보고 피할 방법을 설명할 수 있고, 반복 플레이에서 같은 혼란이 줄며 소리를 꺼도 필수 경고를 읽을 수 있다.
3. **성능·입력·접근성 실기기 검증.** 기존 렌더 캐시와 60Hz 고정 업데이트가 실제 전투 부하에서 어떻게 동작하는지 방/보스·투사체가 많은 장면의 전체 프레임 p95/p99, 입력 지연, 메모리·발열을 측정한다. 목표 기기와 네트워크 조건을 정해 실제 iPhone Safari·Android Chrome·데스크톱 브라우저에서 30분 이상 저장/재개·회전·백그라운드 복귀를 확인한다. 키보드만으로 메뉴와 게임 핵심 동작, 포커스, 텍스트 대비/크기, 애니메이션 완화도 점검한다. 통과: 목표 기기에서 합의한 프레임/입력 기준과 치명적 크래시·진행 손실 0을 달성한다. 초기 측정 기준은 60Hz PC 프레임 16.7ms, 30Hz 모바일 프레임 33.3ms를 참고하되 실제 목표 기기에서 확정한다.
4. **출시 화면과 데이터 신뢰성.** 시작 화면의 8/10층·버전 문구를 현재 제품과 일치시키고, 조작/저장 범위·데이터 이동/삭제·문의 방법을 명확히 한다. 닉네임/쿠키·랭킹 처리 안내를 작성하고 오류 화면에서 재시도·복구 경로를 실제 시험한다. 같은 서버 디스크 백업만 있는 상태를 보완할 외부 백업·복원 시험 및 장애 알림 경로를 정한다. 통과: 새 사용자가 제품 목표와 기록 저장 범위를 이해하고, 저장/배포 장애 시 복구 절차를 운영자가 재현할 수 있다.
5. **릴리스 후보와 제한 공개.** 새 기능을 잠시 고정하고 두 캠페인의 완주/실패/저장·복귀/랭킹/모바일 회귀 체크리스트를 통과시킨다. 소수 사용자에게 제한 공개해 피드백과 오류를 모으고, 막힘·기록 손실·서버 장애를 우선 수정한다. 배포/롤백/백업 복원을 연습한 뒤 공개 범위를 넓힌다. 통과: 치명 이슈 0, 알려진 결함과 우회 방법을 문서화, 운영 담당자가 상태·복구 경로를 확인한 출시 후보.

## 바로 다음 작업 권장
1단계의 **플레이 테스트 기록 양식과 실제 기기/시나리오 목록**부터 만든다. 그다음 8층과 10층을 실제로 플레이해 문제를 분류한다. 이 결과 없이 보스 수치나 아트 규모를 먼저 확대하면 작업 우선순위를 잘못 잡을 수 있다. 사용자 목표 플랫폼·기기와 출시 범위가 정해지면 3~5단계의 통과 수치를 확정한다.

참고: [web.dev Core Web Vitals](https://web.dev/articles/vitals)는 로딩·상호작용 지표를 설명하지만 Canvas 전투 프레임은 별도 측정이 필요하다. [W3C WCAG 2.2](https://www.w3.org/TR/wcag/)는 키보드 조작·포커스 등 접근성 검토의 기준이다. [OWASP ASVS 5.0](https://cornucopia.owasp.org/taxonomy/asvs-5.0)은 웹 서비스의 세션·입력/비즈니스 규칙 검토에 참고할 수 있다.
