# 모바일 화면·지도 개선 8항목 검토

2026-10-13 사용자 첨부 화면/요청 검토. 구현 승인이 아닌 검토 요청이다. 이번 작업은 문서/로컬 커밋만, 런타임 변경·테스트·푸시·배포 없음. 승인 보행 e155065는 별도 누적 미검증 변경이다.

## 권장 방향

진행 순서는 모바일 입력/가로전용 → HUD 배치 이미지 시안/컨펌 → 진입부 안전성/지도 방향 분산 → 문 위치 다양화다. 8번은 판정·저장까지 연결되는 가장 큰 변경이므로 마지막에 분리한다. 숫자와 범위는 제안이며 미확정이다.

## 1·2 브라우저 제약과 기존 코드

styles/mobile.css에는 portrait용 플레이 배치가 따로 있고 회전 안내만 표시한다. src/ui/mobile-ui.js의 전체화면 버튼은 회전 잠금을 요청하지 않는다. 세로 전환 시 진행 중 전투를 멈추고 입력을 해제하며, 돌아올 때 기존 수동 일시정지를 임의 해제하지 않는 흐름이 필요하다. 메인 메뉴/저장 접근도 안내 화면에서 가능하게 남긴다. CSS로 화면 전체를 90도 회전하면 조작 좌표 문제가 생기므로 권장하지 않는다.

[MDN ScreenOrientation.lock](https://developer.mozilla.org/en-US/docs/Web/API/ScreenOrientation/lock)은 지원 범위가 제한적이고 대개 모바일 전체화면에서 허용된다. 실제 기기/브라우저 종류는 제공되지 않아 특정 기기 지원을 단정하지 않는다.

Canvas·조이스틱·액션 버튼은 이미 touch-action:none이지만 헤더/HUD/여백까지 일관 적용되지는 않았다. viewport 메타는 기본 확대를 허용한다. 우선 더블탭을 억제하는 [touch-action:manipulation](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/touch-action)을 UI에 적용한다. OS 확대 기능을 막을 수 있다는 뜻은 아니다. 전체 페이지 확대 금지 메타에만 의존하지 않는다. 목록 드래그, HUD 설명 터치, 두 손가락 게임 조작을 함께 확인해야 한다.

## 3~5 HUD 공간

첨부 화면의 좌우 검은 여백은 .arena의 16:9/높이 제한으로 남은 바깥 공간이다. 현재 체력/유물/스킬/수치는 .arena 기준 DOM 오버레이, 미니맵은 src/world/terrain.js drawMinimap에서 게임좌표(772,12,166,160)에 직접 그린다. CSS 위치 이동만으로 미니맵을 옮길 수 없으므로 별도 Canvas로 분리하고 게임은 중앙 전투 화면에 둔다.

권장 배치: 왼쪽 상단 체력→유물·정수, 왼쪽 하단 스킬→조이스틱, 오른쪽 상단 미니맵→레벨/공격력/공속/이속/DPS, 오른쪽 하단 액션 버튼. XP는 중앙 화면 바깥 하단 또는 여백 내 표시로 조정하되 시안에서 확정한다. 모바일의 주소창/노치/전체화면에 따라 여백 폭을 다시 계산한다. 여백이 적은 기기는 최소 패널 폭을 예약해 중앙 화면을 조금 줄이거나 접기 방식으로 처리하며, 전투 영역으로 덮어쓰기하지 않는다. 정확한 패널 폭·아이콘 수·크기는 이미지 시안 컨펌 후 확정한다.

## 6 지도 편향의 근거와 범위

src/game/engine.js generateFloor의 시작 6방은 (0,0),(1,0),(2,0),(2,1),(1,1),(0,1)로 고정이다. 첫 추가 방은 rooms[2] 부근에서 확장하고 마지막 생성 방을 up으로 지정하며, 보스 추가는 dirs.find로 북/동/남/서 중 첫 유효 방향을 우선한다. 경험한 ‘우상단만’이라는 통계는 아직 재현/측정하지 않았지만, 지도 방향 다양성을 제한하는 코드 근거는 있다.

‘미니맵에서 계단 방 방향’과 ‘그 방 안 계단 오브젝트 위치’를 구분한다. 현재 기본 방 오브젝트 좌표는 objectPoint의 (480,115)이며 보스 후 계단도 별도 고정 좌표 처리다. 첫 단계는 지도 방 방향 분산이고 방 안 계단 위치 분산까지 요구하는 경우 별도 시안/판정 변경으로 다룬다. 최종10층 2방 전용 구조는 일반층 회전 대상과 분리 검토한다.

회전/반사는 방 인덱스를 바꾸지 않고 좌표만 변환하되, 첫방→튜토리얼방의 안내/문 방향과 neighbor 제한, 귀환 길 찾기·열쇠 탈출 접근방 규칙을 같이 맞춘다. 특정 방향이 나올 확률을 균등하게 제안하지만 매 플레이/각층에서 네 방향이 모두 나온다는 보장은 하지 않는다.

## 7·8 진입 안전성 및 문 공유

room-shapes.js의 compact는 vertical/horizontal 벽을 동시에 추가해 네 방향 모두 좁아질 수 있다. 기본 props를 무작정 줄이기보다 진입부 보호영역을 정의하고 그 구간을 좁히는 벽을 제한한다. 플레이어 반경14, 몹/거인 반경, 회피 공간, 진입 직후 적 위치와 유예 시간을 고려해 입구에서 방 중심/상호작용 대상까지 도달 가능해야 한다. 단순 안전 스폰 성공만으로 통로 연결성을 판정하지 않는다.

simulation.js 출입 판정은 상하문 x=480±40, 좌우문 y=270±35에 고정, 반대편 입장 위치도 기존 좌표를 따른다. object-positions.js가 문 주변 회피를 중앙4개 진입점으로 계산하고 벽/장식도 기존 문 위치 전제를 갖는다. shared-edge 문 좌표를 한곳에서 제공하는 방식으로 바꾸고 양쪽 방·벽 구멍·충돌·입장·점멸·봉쇄 표시·장식이 함께 참조해야 한다. 미니맵은 연결 자체만 간단히 표시해도 된다.

문 후보는 벽 길이의 중앙 구간(예: 30~70%)부터 시작하고 코너·장애물·보스 패턴·계단과 겹침을 배제한다. 정확 범위는 시안/검증 뒤 확정한다. 문을 이동할 때 보호영역도 같이 옮겨 7번 협소 문제를 재발시키지 않는다.

## 저장/검증 계획 — 아직 실행하지 않음

HUD/입력은 기존 원정에도 적용 가능. 지도/문/내부벽 생성 변경은 새 원정 generationVersion 경계로 구분하고 기존 저장의 방 좌표/장애물을 재배치하지 않는다. 문 좌표가 없는 구저장은 기존 중앙 문 fallback으로 유지한다. 저장 스키마 유효성·랭킹 버전 정책은 구현 때 확인하며 임의 초기화/시즌 종료는 하지 않는다.

사용자 배포 지시 때 누적 보행 변경도 함께 검증한다: 가로/세로 전환 정지·재개·입력 해제, 더블탭·복수 터치·목록 드래그, 최대 체력/유물/스킬의 HUD 겹침, 여러 가로 해상도·safe area·브라우저 전체화면, 다수 지도 시드의 목표 방향/동선/문 짝/출입/귀환/보스/구저장, 모든 진입점 도달성·복도 제한. 에뮬레이션과 실제 모바일 검증은 구분한다. 이번 검토에서는 실행하지 않았다.
